# AegisDNS revenue plan

Prepared 9 September 2026. This is an operating plan, not a revenue forecast.

## The business

Keep the entire MIT-licensed product free. Sell maintainer time to organizations and invite recurring sponsorship for public maintenance. Near-term priority: one scoped, paid engineering or deployment engagement. Longer-term priority: repeat sponsors who fund maintenance without creating an unmanageable support obligation.

The project's public GitHub API showed 0 stars and 0 forks when checked. Those are distribution signals, not a count of installations. There is not yet evidence to price sponsorship as access to a large audience. Sell a clearly useful outcome first; do not promise reach, adoption, security certification or financial returns.

These changes are local until released/published. The existing Sponsors destination is already public. No new financial account, payment processor or recurring charge was created.

## First 30 days

1. **Release and verify the path.** Publish these project changes through your normal release process. Check the Sponsor button while signed out, then verify payout readiness in your private GitHub Sponsors settings. Update the profile introduction using the draft below. Do not share bank, tax or account credentials in the repository.
2. **Create one piece of proof.** Document a reproducible deployment with hardware, versions, test method and known limitations. Use synthetic workloads and publish the procedure. Avoid absolute claims such as catching all zero-day threats.
3. **Choose a narrow buyer.** Start with a small IT consultancy, managed service provider or Linux appliance vendor that has a real packaging, migration or integration problem. Do not sell 24/7 support as a solo maintainer.
4. **Have ten relevant conversations.** Use existing contacts and communities that permit commercial discussion. Ask about an actual deployment problem. Send individually tailored messages yourself; no bulk scraping, unsolicited mailing automation or invented customer claims.
5. **Quote one bounded engagement.** Write scope, exclusions, acceptance tests, delivery milestones, ownership/license and support boundary. Agree a private communication channel and billing arrangements. Do not use GitHub sponsorship as a substitute for a services agreement.
6. **Deliver and ask for continued funding.** Release the agreed public improvement and request permission for a case study or sponsor acknowledgment. Offer recurring maintenance sponsorship if the organization sees continuing value.

## Pricing hypotheses to validate

Public suggested sponsorships are $250/month and $1,000/month. Those are starting points for conversations, not existing provider tiers or guaranteed market demand.

For services, estimate hours, multiply by a sustainable rate, and explicitly price uncertainty and post-delivery support. Start with a small paid discovery task when the scope is unclear. Do not promise a fixed deadline before checking availability. Actual service prices belong in a written quote.

Illustrative arithmetic: four $250/month sponsors plus one $1,000/month sponsor produce $2,000/month gross. A separately agreed $1,500 engineering project would make that month's gross receipts $3,500. This is a scenario, not an earnings prediction; it excludes fees, expenses and taxes. Delivery time makes project revenue less scalable than recurring sponsorship.

## Scope template

- Organization and decision-maker
- Problem and measurable outcome
- Deliverables and excluded work
- Reproducible acceptance tests and required environment
- Estimate, milestones and availability
- Written quote and separately agreed payment arrangements
- Open-source release and attribution terms
- Access requirements and agreed private communication channel
- Warranty/support boundary to agree before work starts

## Run this without adding surveillance

Track qualified inquiries, proposals, accepted work, gross receipts, delivery hours and renewals manually. Use GitHub's sponsor dashboard for actual sponsorship status. Do not add install IDs, query collection or browser tracking to measure monetization. Never label a link click as revenue. Publish aggregate maintenance updates; do not publish sponsor identities or payment details without permission.

## Research

- [Pi-hole funding](https://pi-hole.net/donate/): an existing free DNS project uses recurring sponsorship and disclosed affiliate referrals. AegisDNS implements sponsorship; no affiliate program or referral payment is implied.
- [About GitHub Sponsors](https://docs.github.com/en/sponsors/getting-started-with-github-sponsors/about-github-sponsors): supports recurring and one-time sponsorship. India is listed as supported. Its published fees distinguish personal and organization sponsorships; verify current terms when setting prices.
- [Set up a Sponsors account](https://docs.github.com/en/sponsors/receiving-sponsorships-through-github-sponsors/setting-up-github-sponsors-for-your-personal-account): profile, tiers, bank/tax details and approval are controlled through the owner's account. The existing public profile is verified; private payout status was not inspected.

The recommendation to prioritize scoped business work before relying on substantial sponsor income is an inference from the project's current public reach and the solo-maintainer constraint, not a claim that these sources guarantee revenue.
